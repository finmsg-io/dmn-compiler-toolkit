## Outcome

Every diagnostic exposed through the compiler module uses one immutable shared contract that
identifies its severity, compiler phase, stable code, originating source, and model identity where
available. Existing P1.4 import diagnostics are converted without changing their codes, ordering,
or graph-loading behavior. The result supports deterministic machine processing and provides the
foundation for aggregating diagnostics from later compiler phases.

## In scope

- Introduce a shared immutable compiler diagnostic contract.
- Define stable severity and compiler-phase values.
- Retain the four P1.4 `DMN-IMPORT-*` diagnostic codes.
- Attach the importing `DmnSourceId` to every import diagnostic.
- Attach namespace and model name when the originating model is available.
- Retain import-request context, related source identities, and canonical cycle paths.
- Define and test deterministic diagnostic ordering.
- Make `DmnModelLoadResult` expose shared diagnostics.
- Preserve P1.4 partial-graph and validity behavior.
- Document required fields and explicit absence semantics.

## Non-goals

- Aggregating XML, FEEL, semantic-analysis, Runtime IR, optimizer, or generator diagnostics.
- Adding line, column, range, model-path, or expression-path data unavailable from the producer.
- Redesigning lower-level diagnostic contracts.
- Implementing the P1.6 model-set result or P1.7 compiler facade.
- Warning suppression, localization, rendering, persistence, quick fixes, or help URLs.
- Changing P1.4 traversal, recovery, cycle, or duplicate rules.

## Architectural constraints

- The shared contract belongs to `dmn-compiler`; lower-level modules must not depend on it.
- Later orchestration adapts lower-level diagnostics at the compiler boundary.
- Diagnostics and nested collections are immutable.
- P1.4 diagnostic codes retain their meaning.
- Ordering is independent of discovery order, maps, and resolver registration.
- Expected compilation problems remain result data rather than unchecked exceptions.
- Severity and phase are closed, type-safe values.
- Source identity uses `DmnSourceId`; model identity remains a separate concept.
- Optional fields use explicit absence rather than `null` or empty-string sentinels.
- The contract remains extensible with source locations and semantic paths.

## Proposed contract

```java
public record DmnCompilerDiagnostic(
    DmnDiagnosticSeverity severity,
    DmnCompilerPhase phase,
    String code,
    String message,
    DmnDiagnosticOrigin origin,
    Optional<DmnImportRequest> importRequest,
    List<DmnSourceId> relatedSourceIds,
    List<DmnSourceId> cyclePath) {
}
```

```java
public enum DmnDiagnosticSeverity {
  INFO,
  WARNING,
  ERROR
}
```

```java
public enum DmnCompilerPhase {
  SOURCE_RESOLUTION,
  XML_FRONTEND,
  FEEL_PARSING,
  SEMANTIC_ANALYSIS,
  RUNTIME_IR_LOWERING,
  OPTIMIZATION,
  GENERATION
}
```

```java
public record DmnDiagnosticOrigin(
    DmnSourceId sourceId,
    Optional<DmnModelIdentity> modelIdentity,
    Optional<Integer> importIndex) {
}
```

Exact type names may change during implementation, but observable fields and semantics remain as
specified.

## Field semantics

| Field | Requirement |
| --- | --- |
| `severity` | Required; P1.4 import failures use `ERROR` |
| `phase` | Required; P1.4 import diagnostics use `SOURCE_RESOLUTION` |
| `code` | Required, stable, non-blank machine identifier |
| `message` | Required, non-blank human explanation |
| `origin.sourceId` | Required stable identity of the originating source |
| `origin.modelIdentity` | Namespace and model name when the model parsed successfully |
| `origin.importIndex` | Present for a specific import declaration |
| `relatedSourceIds` | Sorted identities relevant to ambiguity, duplication, or cycles |
| `cyclePath` | Directed canonical closed path, used only for cycle diagnostics |

`INFO` and `WARNING` are defined but need no producer in this slice. All P1.4 import diagnostics
use severity `ERROR` and phase `SOURCE_RESOLUTION`.

## Acceptance scenarios

1. A missing import reports `ERROR`, `SOURCE_RESOLUTION`, `DMN-IMPORT-MISSING`, the importing
   source, parsed model identity, and import index.
2. An ambiguous import retains candidate source identities in lexical order.
3. Conflicting bytes report `DMN-IMPORT-DUPLICATE` with importing and conflicting identities.
4. Duplicate namespace/model-name identities report the introducing import and sorted identities.
5. Direct and transitive cycles retain the canonical closed path established by P1.4.
6. Every aggregated import failure contains severity, phase, code, message, and source identity.
7. Unavailable model identity is explicitly absent, never `null` or an empty-string sentinel.
8. Blank codes/messages, null required fields, negative indices, and invalid cycle paths fail fast.
9. A valid graph has no diagnostics, `isValid()` is true, and `hasErrors()` is false.
10. Direct contract tests prove `INFO` and `WARNING` do not make `hasErrors()` true.
11. One or more `ERROR` diagnostics make `hasErrors()` true and `isValid()` false.
12. Reordered discovery or resolver registration produces equivalent ordered diagnostics.
13. All P1.4 behavior and P1.3 resource-limit scenarios remain unchanged.

## Deterministic ordering

Use an explicit comparator ordered by:

1. originating source identity;
2. optional import index, absent first;
3. compiler phase;
4. severity;
5. diagnostic code;
6. related source identities;
7. canonical cycle path;
8. message as a final tie-breaker.

Enum ordinal and record declaration order are not undocumented compatibility guarantees.

## Open decisions

Resolved for this slice:

- codes are validated strings supplied through constants in `DmnDiagnosticCodes`;
- the P1.4-specific public diagnostic record and enum were replaced rather than adapted;
- model identity is an optional `DmnModelIdentity` containing namespace and name;
- `hasErrors()` checks specifically for `ERROR`, so `INFO` and `WARNING` remain valid;
- the optional import index remains on `DmnDiagnosticOrigin` until a richer path exists;
- the optional import request retains structured resolution context;
- source ranges remain deferred until a producing phase is integrated.

## Suggested delivery sequence

1. Define severity, phase, model identity, and diagnostic-origin contracts.
2. Define and test the shared diagnostic record and explicit comparator.
3. Adapt missing, ambiguous, duplicate, and cycle diagnostics.
4. Update result validity to depend on `ERROR` severity.
5. Remove or internalize the P1.4-specific public representation.
6. Run compiler tests and the complete reactor.
7. Update documentation and attach evidence to P1.5.

## Result

Implemented `DmnCompilerDiagnostic`, `DmnDiagnosticSeverity`, `DmnCompilerPhase`,
`DmnDiagnosticOrigin`, `DmnModelIdentity`, and string constants in `DmnDiagnosticCodes`.
All P1.4 import classifications now use severity `ERROR`, phase `SOURCE_RESOLUTION`, the importing
source and parsed model identity, optional import index and request, sorted related identities, and
the existing canonical cycle path. The explicit comparator follows the ordering specified above.

`DmnModelLoadResult` now exposes shared diagnostics and derives validity only from `ERROR`
severity. Five `DmnCompilerDiagnosticTest` contract tests and all 14 `DmnModelLoaderTest`
scenarios pass; all 32 compiler tests and the complete eight-project Maven reactor pass. Strict
MkDocs validation and `git diff --check` pass. No new ADR was required. Lower-phase adapters,
source ranges, semantic paths, and cross-phase aggregation remain deferred as specified.
